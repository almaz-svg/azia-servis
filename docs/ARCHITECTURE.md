# Сынақ — архитектура

Статус: черновик v0.1, 2026-11-10. Основа: «ТЗ: Сынақ — платформа оценки учебников и учебных часов».
Написано для: двух разработчиков команды.

Здесь описано, как устроен проект, чтобы он не ломался при доработках и на защите. Всё, что ТЗ не определяет, решено по умолчанию и помечено в разделе 15.

---

## 1. Принципы

1. **Расчёты — чистый код.** Вся статистика живёт в `src/core`. В ней нет React, DOM, сети. Её можно тестировать в Node и проверять числа без браузера.
2. **Один источник чисел.** Экран, экспорт .docx, текст обоснования и LLM берут данные из одного объекта `Analysis`. Нигде число не пересчитывается заново.
3. **Демо не зависит от сети.** Вся работа методиста идёт в браузере. Сеть нужна только апробации, и апробация имеет запасной режим (раздел 13).
4. **Вход проверяется всегда.** Excel, ответы API и текст LLM проходят валидацию. Ошибка сообщает код, лист, строку и колонку, а не «что-то пошло не так».
5. **База закрыта по умолчанию.** Анонимный клиент работает только через три функции (RPC). Прямого доступа к таблицам нет.
6. **Методика версионируется.** Пороги лежат в одном объекте с номером версии. Версия и идентификатор датасета попадают в каждый экспорт и в текст обоснования.
7. **Без лишних слоёв.** Предметы и классы — это данные, а не код. Но абстракции, которых нет в MVP, не добавляем.

  config.toml    пока не создан: `supabase init` перед `supabase start`

**Правило зависимостей:** `core ← workers ← features ← app`. `core` не импортирует ничего из проекта, кроме себя. Сейчас проверяется тестом `src/core/boundaries.test.ts`. ESLint и CI пока не подключены (раздел 17).

**Правило текстов:** в `features/**/*.tsx` нет строк с кириллицей и казахскими буквами. Весь текст идёт через `t('key')`. Тест проверяет, что у каждого ключа есть перевод в `ru.json` и `kk.json`.

## 4. Данные

### 4.1 Где что хранится

| Данные | Где | Срок жизни |
|---|---|---|
| Строки «Результаты» и «Уроки» | Память Worker + IndexedDB | До кнопки «Очистить данные» |
| Демо-датасет | Генерируется кодом по фиксированному seed | Не хранится |
| Настройки методики | Константа `ANALYSIS_CONFIG` в коде | Версия пишется в каждый экспорт |
| Сессия апробации | Postgres, `trial_sessions` | До закрытия |
| Участники и ответы | Postgres; наружу отдаются только агрегаты | До закрытия сессии |
| `device_key` | localStorage участника | На устройстве |
| Неотправленные ответы | localStorage участника | Пока сервер не подтвердит |

По ТЗ ФИО учеников нет. Чтобы не допустить персональные данные в файл, парсер блокирует загрузку, если в заголовках есть «ФИО», «Фамилия» или «Имя» (код `err.personalData`).

### 4.2 Типы данных (`src/core/types.ts`)

```ts
export type Textbook = 'А' | 'Б';
export type SchoolType = 'город' | 'село';

/** Лист «Результаты»: одна строка = класс × раздел × учебник */
export interface ResultRow {
  year: string;            // Учебный год, «2025-2026»
  district: string;        // Район
  school: string;          // Школа, код «Т-01»
  schoolType: SchoolType;  // Тип
  textbook: Textbook;      // Учебник
  grade: string;           // Класс, «5А»
  topic: string;           // Раздел
  students: number;        // Учеников
  sorPct: number;          // СОР %, 0–100
  entryPct: number;        // Входной уровень %, 0–100
}

/** Лист «Уроки»: одна строка = класс × раздел */
export interface LessonRow {
  year: string;
  school: string;
  grade: string;
  topic: string;
  plannedHours: number;    // Часов по плану
  actualHours: number;     // Часов по факту
}

export interface Dataset {
  id: string;                  // SHA-256 нормализованных строк
  source: 'demo' | 'upload';   // управляет меткой «Демо-данные» на всех экранах
  results: ResultRow[];
  lessons: LessonRow[];        // пусто, если листа «Уроки» нет
}
```

### 4.3 Идентичность датасета

`dataset.id` — это SHA-256 от строк, отсортированных по ключу. Ключ кэша расчётов: `${dataset.id}:${config.version}`. Экспорт пишет оба значения, так что любую записку можно воспроизвести.

## 5. Основные потоки

**5.1 Загрузка.** Файл → Worker `parse` (SheetJS, затем валидация по схемам) → либо `dataset`, либо список ошибок (до 50). Ошибки блокируют анализ: частичная загрузка не принимается без явного согласия. Успешный датасет сохраняется в IndexedDB.

**5.2 Анализ.** Worker `analyze(dataset, config)` → `Analysis`: статусы тем, сравнение учебников с поправкой и без, кривые «цена часа». Результат кэшируется по `analysisKey`. Экраны читают только его.

**5.3 Перераспределение часов.** Worker `optimize(analysisKey, request)` → `HourPlan`. Кнопка «Оптимизировать» и ползунки используют одни и те же кривые. Прогноз берётся из кэша, поэтому ответ укладывается в 100 мс.

**5.4 Апробация.** Участник: `join_trial` → 3 вопроса → `submit_trial`. Если сети нет, ответ уходит в очередь в localStorage и повторяется с тем же `device_key`. Сервер принимает повтор идемпотентно. Проектор: `trial_stats` каждую секунду.

**5.5 Текст обоснования.** `Analysis` → `buildNoteFacts()` (только числа и коды) → сразу показывается шаблон `renderTemplateNote(facts)`. Если LLM включён, в фоне запрашивается `/api/note`. Его ответ заменяет шаблон только после `validateNote(text, facts)`: каждое число в тексте должно быть в `facts`. Если LLM не ответил за 8 с или не прошёл проверку, остаётся шаблон.

**5.6 Экспорт.** Копирование текста (P0) и .docx с таблицей «было → стало» (P1) собираются в браузере. Оба содержат метку «Демо-данные» (если она есть), `configVersion` и `analysisKey`.

## 6. Контракты

### 6.1 Протокол Worker

```ts
// Фактическая реализация: src/workers/protocol.ts (К3).
// Черновик v0.1 использовал `optimize`, `analysisKey`, `config` и поле `ok`. Они заменены этим протоколом.
export type WorkerRequest =
  | { id: number; type: 'parse'; fileName: string; bytes: ArrayBuffer }
  | { id: number; type: 'analyze'; dataset: Dataset; scope: ScopeFilter }
  | { id: number; type: 'plan'; dataset: Dataset; request: HourRequest };

export type ParseResult =
  | { ok: true; dataset: Dataset }
  | { ok: false; errors: AppError[] };

export type WorkerResponse =
  | { id: number; type: 'parse'; result: ParseResult }
  | { id: number; type: 'analyze'; result: Analysis }
  | { id: number; type: 'plan'; result: HourView }
  | { id: number; type: 'error'; message: string };

/** code — это ключ i18n. Worker не знает языка интерфейса. */
export interface AppError {
  code: string;                                   // 'err.noSheet', 'err.badValue', …
  params?: Record<string, string | number>;       // подставляются в текст
  where?: { sheet: string; row?: number; column?: string };
}
```

Коды ошибок совпадают с ID из раздела «Ошибки» ТЗ (`err.noSheet`, `err.badValue`, `err.format`, `err.offline`, `err.trialClosed`). Дополнительно введены `err.missingColumn`, `err.personalData`, `err.duplicateRow`. Полный список — в `src/core/errors.ts`. Новые коды добавляются только туда.

### 6.2 Текст обоснования: API

`POST /api/note` принимает `NoteFacts` (JSON, не больше 4 КБ) и возвращает `{ text: string }` (не больше 600 символов). Строки школ в запрос не попадают. Ключ LLM хранится только в переменных окружения Vercel.

### 6.3 Апробация: схема Supabase

```sql
create table trial_sessions (
  id         text primary key,                 -- код для QR, 6 символов, случайный
  status     text not null default 'open' check (status in ('open','closed')),
  created_at timestamptz not null default now()
);

create table trial_members (                    -- назначение группы при входе
  session_id text not null references trial_sessions(id),
  device_key uuid not null,
  grp        char(1) not null check (grp in ('A','B')),
  primary key (session_id, device_key)
);

create table trial_answers (                    -- один ответ с устройства на сессию
  session_id text not null,
  device_key uuid not null,
  lang       text not null check (lang in ('kk','ru')),
  correct    smallint not null check (correct between 0 and 3),
  created_at timestamptz not null default now(),
  primary key (session_id, device_key),
  foreign key (session_id, device_key) references trial_members
);

create table trial_keys (                       -- эталон; ни одна роль anon не читает
  question       smallint primary key check (question between 1 and 3),
  correct_choice smallint not null
);

alter table trial_sessions enable row level security;   -- то же для всех таблиц
-- политик для anon нет: доступ только через функции
```

Все функции — `security definer` с `set search_path = public`. Права `execute` выдаются только `anon` на три функции ниже.

| Функция | Вызывает | Поведение |
|---|---|---|
| `join_trial(session, device)` | Участник | Блокирует строку сессии (`for update`). Если участник уже есть, возвращает его группу. Иначе назначает меньшую из A и B, а при равенстве — случайно. Ошибка, если сессия закрыта или не существует. |
| `submit_trial(session, device, lang, choices smallint[3])` | Участник | Идемпотентно: повтор не меняет первый ответ. Проверяет, что участник в сессии и сессия открыта. Считает верные ответы по `trial_keys`. Ничего не возвращает: по ТЗ результат видно только на проекторе. |
| `trial_stats(session)` | Проектор | Возвращает для каждой группы `n`, `Σx`, `Σx²`. Если в группе меньше 5 ответов, поля этой группы возвращаются как `null` (приватность). |

Почему функции, а не прямой доступ: политика ТЗ `with check (true)` позволяла бы любому записать `grp` и `correct`, а `select` с `using (true)` отдавал бы все ответы. Функции решают обе проблемы.

Почему `join_trial` вместо `/api/assign`: два одновременных входа в API дают обоим группу «А», и разница становится 2. Блокировка строки сессии в одной транзакции исключает это.

## 7. Расчёты (спецификация для `src/core`)

**7.1 Освоение.** `освоение(тема, учебник) = Σ(students·sorPct) / Σ students` по строкам этого учебника.

**7.2 Статус темы.** Правила проверяются по порядку, первое совпадение побеждает:

1. **Мало данных:** на каком-либо учебнике меньше `minClassesPerTextbook` (8) классов.
2. **Проблема учебника:** `|Δ| ≥ 7 п.п.` и доверительный интервал не содержит 0. Проблемным считается учебник с меньшим скорректированным освоением.
3. **Проблема программы:** освоение ниже 60% на обоих учебниках, и пункт 2 не выполнен.
4. **Норма:** всё остальное.

Если у темы один учебник, пункт 2 не применяется, и подсказка говорит «сравнивать не с чем».

**7.3 Сравнение учебников с поправкой.** WLS-регрессия по строкам «класс × раздел»: `sorPct ~ 1 + [учебник = Б] + entryPct`, веса — `students`. `Δ = β(Б) − β(А)`, то есть знак отрицательный, если Б слабее. Стандартные ошибки кластеризованы по школе. Интервал: `Δ ± t(0,975; G−1) · SE`, где `G` — число школ. Для демо это примерно ±2,1, а не ±1,96 (см. раздел 15).

**7.4 Кривая «цена часа».** Для пары «тема × учебник»: `s(h, L) = M·(1 − e^(−h/τ)) + β·(L − L̄)`. Параметр `τ` перебирается сеткой (шаг 0,5 от 1 до 80). При фиксированном `τ` модель линейна по `M` и `β`, поэтому они находятся замкнутой формулой МНК. Выбирается `τ` с минимальной суммой квадратов ошибок. Ограничения: `0 ≤ M ≤ 100`. Если кривой нельзя построить (меньше 6 классов или все часы одинаковы), пишем «часы не различаются» — кривую не строим.

**7.5 Часов до 70%.** `h70 = −τ · ln(1 − 70 / M)`, при `L = L̄`. Если `M ≤ 70`, пишем «не достигается». Если `h70` больше наибольших наблюдаемых часов, добавляем пометку «экстраполяция».

**7.6 Отдача следующего часа.** `m(h+1) − m(h)` по кривой, в п.п.

**7.7 Оптимизатор.** Годовой объём темы фиксирован. На каждом шаге перенос 1 часа от темы с минимальной потерей к теме с максимальным выигрышем. Чистый выигрыш шага = выигрыш получателя − потеря донора. Остановка, когда чистый выигрыш меньше 0,3 п.п. Ограничения: `±20%` от исходных часов темы, не меньше минимума программы. Тай-брейк — по коду темы, чтобы результат был детерминированным. Лимит итераций — 20 × общий объём часов.

**7.8 Прогноз.** `Σ(доля часов темы × Δосвоения темы)`. На экране помечен как «оценка модели».

**7.9 Вердикт апробации.** По сумматорам `n`, `Σx`, `Σx²` для каждой группы:
- `d = mean(B) − mean(A)`, `SE = sqrt(s²_A/n_A + s²_B/n_B)`, интервал `d ± 1,96·SE`.
- **Надёжен:** интервал не содержит 0 и `min(n_A, n_B) ≥ 20`.
- **Мало ответов:** `n` меньше 20 в какой-то группе или интервал содержит 0 при `n < 20`. Оценка нужного числа: `n ≈ (1,96·√2·s_pooled / |d|)²` на группу, минус текущее `n`.
- **Разницы не видно:** интервал содержит 0 и `n ≥ 20` в каждой группе.

## 8. Надёжность: риски и меры

| Риск | Мера |
|---|---|
| Демо падает на сцене из-за сети или Supabase | Вся аналитика работает в браузере. Демо-датасет зашит в код. Запасной вариант: `next start` на ноутбуке и локальный Supabase. Видео демо лежит на диске. |
| Экран, экспорт и записка расходятся по числам | Один объект `Analysis`, один `analysisKey`. Валидатор текста проверяет, что каждое число есть в `facts`. |
| Перезагрузка страницы теряет загруженный файл | Датасет в IndexedDB, есть «Очистить данные». |
| Расчёт подвешивает интерфейс | Расчёты только в Worker. Результат кэшируется по `analysisKey`. |
| Плохой Excel даёт тихо неверные цифры | Валидация по схемам. Ошибки блокируют анализ. Каждая ошибка указывает лист, строку и колонку. |
| Две параллельные записи нарушают баланс групп | `join_trial` блокирует строку сессии. Тест: 50 параллельных входов, `|A−B| ≤ 1`. |
| Двойной голос с одного устройства | `primary key (session_id, device_key)` и идемпотентный `submit_trial`. Кнопка «Ответить» блокируется после нажатия. |
| Подделка верных ответов | Подсчёт на сервере по `trial_keys`, которые anon не читает. |
| Утечка ответов через API | Таблицы закрыты RLS. Агрегаты при группе меньше 5 скрыты. |
| В казахском интерфейсе пропущена строка | Тест паритета ключей `ru.json` и `kk.json` ломает сборку. |
| Статистика даёт ложный вывод | Пороги и условия показаны в подсказке «почему такой статус». Интервалы на экране. Кластеризация по школе. |
| LLM придумывает число | Текст LLM принимается только после проверки чисел. Шаблон показывается сразу, LLM работает в фоне. |
| Проектор отстаёт от телефонов | Опрос `trial_stats` раз в 1 с. Это укладывается в требование «меньше 2 с». |
| Сеть на площадке пропадает во время апробации | Очередь ответов в localStorage с повтором. Запасной режим `snapshot` (раздел 13). |
| Пороги меняются в последний момент | Версия методики в `ANALYSIS_CONFIG`. Версия пишется в каждый экспорт. |
| Демо не воспроизводится | Генератор на фиксированном seed, округление до целых. Golden-тест на `dataset.id` и статусы. |
| Срыв сроков | Порядок отсечения (раздел 14): что резать первым. |

## 9. Безопасность и приватность

- Данные школ не покидают браузер. На сервер уходят только ответы участников и (если включён LLM) числа для текста.
- `anon key` публичный, поэтому безопасность держится на RLS и функциях, а не на ключе.
- Ключ LLM и `service_role` на клиент не попадают. Проверка: в бандле нет этих строк (тест на сборке).
- Идентификатор сессии: 6 символов из случайного источника, около 30 бит. Угадать чужую сессию сложно, но на время хакатона этого достаточно.
- `device_key` — случайный UUID, не связан с людьми и IP. IP не сохраняем.
- Вход без логина, роли и админки — по ТЗ. Значит, закрыть сессию может любой, кто знает код. Это принятый риск хакатона. Если понадобится, добавим токен хоста при создании сессии.

## 10. Локализация

- Строки только в `ru.json` и `kk.json` с одинаковыми ключами.
- Склонения русских чисел через `Intl.PluralRules`. Казахские падежи после числа проверяются функцией, как в ТЗ.
- Десятичная запятая и «» — через форматтеры, не вручную.
- Сокращения БЖБ, ТЖБ, ҚТЖ не переводятся на русский в казахском интерфейсе.
- Казахские строки проверяет носитель языка до защиты (пункт чек-листа ТЗ).

- 50 параллельных `join_trial`: `|A−B| ≤ 1`.

- Офлайн: отключить сеть, аналитика работает, ответ участника попадает в очередь и уходит после восстановления связи.

**Приёмка:** чек-лист ТЗ «Критерии приёмки» пройден три раза подряд без ошибок.

## 15. Отклонения от ТЗ и принятые по умолчанию решения

**Отклонения (предлагаю согласовать):**

1. `/api/assign` заменён функцией `join_trial` в базе. Причина: атомарность (раздел 6.3).
2. Политики RLS из ТЗ заменены функциями. Причина: клиент не должен писать `grp` и `correct`, и не должен читать все ответы.
3. Realtime заменён опросом `trial_stats` раз в 1 с. Требование «< 2 с» выполняется, а движущихся частей меньше. Realtime остаётся улучшением, если будет время.
4. В поправке `1,96` заменено на `t(0,975; G−1)` с кластеризацией по школе. Причина: при 20 школах `1,96` даёт слишком узкий интервал.
5. Чек-лист «Группы А и Б отличаются по числу ответов не больше чем на 1» заменяется на «по числу участников». Группа назначается при входе, и ответы могут не совпасть, если кто-то не ответил.
6. В ТЗ два противоречащих правила назначения групп: «случайно, чередуется блоками по 2» и «если группы равны, случайно, иначе в меньшую». Беру второе: оно даёт `|A−B| ≤ 1` без привязки к порядку входа.

**Решения по умолчанию (ТЗ их не задаёт):**

- Порядок статусов: Мало данных → Проблема учебника → Проблема программы → Норма (раздел 7.2).
- Тема с одним учебником не получает статус «Проблема учебника».
- Знак Δ: `освоение(Б) − освоение(А)`. Проблемный учебник — тот, у которого скорректированное освоение ниже.
- Регрессия — WLS с весами по числу учеников, ошибки кластеризованы по школе.
- Чистый выигрыш шага оптимизатора и остановка при 0,3 п.п. (раздел 7.7).
- Прогноз «взвешенный по часам» — средневзвешенное по доле часов темы. Помечен как оценка.
- Ситуации для кривой: «не достигается» при `M ≤ 70`, пометка «экстраполяция».
- Скрытие агрегатов при группе меньше 5 ответов (приватность).
- Пороги зашиты в код, а не редактируются в UI (в ТЗ «админка порогов — не делаем»), но показываются в подсказках.

**Проверка:**
- 125 юнит-тестов проходят. Приёмка ТЗ на демо: «Обыкновенные дроби» — «Проблема учебника» (Б на −10,3 п.п., интервал [−11,6; −9,0]), «Проценты» — «Проблема программы» (51% и 51%).

- Строки ошибок ядра — ключи словаря, а не русский текст. Это обязательное условие для казахского интерфейса.

**Что осталось открытым:**

### К3 — сделано (ч. 9–13)

- **Оптимизатор (`src/core/hours.ts`):** единица — тема (среднее фактическое число часов на класс). Освоение темы по модели — смесь кривых учебников с весами по числу классов. Авто-режим по 7.7: на каждом шаге пара «донор → получатель» по чистому выигрышу, остановка при выигрыше меньше 0,3 п.п., лимит 20 × сумма часов. Ручной шаг ±1 час: сумма не меняется, донор или получатель выбирается тем же правилом.

- **Сырой интервал:** `compare.ts` отдаёт 95%-интервал и для разницы без поправки (регрессия на один учебник, кластеры по школе). Переключатель меняет вывод, а не только точку.

**Решения, принятые в К3 (ТЗ их не задаёт):**
- Сумма часов фиксирована по всей параллели, а не по каждой теме (так в ТЗ). Формулировка «годовой объём темы» в 7.7 понята как опечатка.

- Ручной «+» или «−» всегда компенсируется автоматически: показываем, у какой темы час взят или кому передан, и выигрыш шага.

**Не сделано или открыто:**
- Интеграционные тесты RPC на настоящем Supabase: нет проекта и Docker. Функции покрыты тестами на pglite (`supabase/tests`).
- **Демо-данные:** оптимизатор переносит один час. Предельная отдача тем почти одинакова (0,35–0,75 п.п. за час), поэтому первый перенос проходит порог 0,3 п.п., а следующие — нет. Пример ТЗ «на 6 часов больше» не воспроизводится. Пересмотр генератора влияет на приёмку К2, поэтому решает методист.
- Прогноз по 7.8 усредняет по темам. При одном переносе он даёт около +0,04 п.п. Если нужна сумма, меняется формула 7.8.
- Казахские строки К3 — перевод без проверки носителем (см. раздел 16, пункт 4).
